# Ideal Day agent notes

- Production data source of truth: the D1 database bound to the private Sites app at `https://ideal-day-sites.example`. Local D1 is disposable development data and must never be promoted over production.
- The local Hermes `ideal-day` profile runs two bounded paths: Luna low + Fast for immediate conversation, and Terra low + standard tier for durable record/workspace compilation. D1 is durable memory; every bridge attempt uses an isolated Hermes session so retries cannot accumulate prompt history.
- Linked sources are fetched and cached by the bridge before durable compilation; Hermes web search is a narrow fallback. Structured output gets one local JSON repair and at most one in-session correction, and a job fails after three attempts instead of retrying forever.
- The one in-session correction budget is shared by JSON and explicitly safe pre-commit composition failures. Preserve structured validation issues; never replay an uncertain network/server failure as a correction. Each lease (including a manual retry) gets a fresh Hermes session. The app refuses mismatched catalog versions before leasing; the worker fingerprints bridge source between jobs and asks its launcher to reload on exit code 75.
- A self-healing Windows task named `Ideal Day Hermes Bridge` runs the short `bridge/watch-ideal-day.ps1` supervisor every five minutes. The supervisor launches `bridge/start-ideal-day.ps1` only when the worker is absent; reinstall the task with `bridge/install-ideal-day-task.ps1`. Startup/worker failures are written to `%LOCALAPPDATA%\IdealDay\logs\bridge.log`, with raw worker output beside it. The bridge makes authenticated outbound HTTPS requests to production; no inbound localhost tunnel is used.
- Bridge secrets are user-bound DPAPI files in `%LOCALAPPDATA%\IdealDay`, never repository files. Rotate both the Sites bypass token and `IDEAL_DAY_BRIDGE_TOKEN` together with the local copies.
- Agent work is durable in D1. The UI shows work immediately while a message is saved and continues while the bridge heartbeat is online; queued offline work says Luna will catch up.
- Completed activity work writes one durable `conversation_artifacts` receipt from validated actions that actually committed. Never infer success from a workspace render change or remove a receipt when the user views its result.
- Catalog v3 stores durable domain data in validated base or variant-scoped activity records and uses workspace revisions only for composition. Product/device records are subject roots; owned records carry the same `subjectKey`. Agents may emit bounded `recordActions`, `workspaceActions`, `activityMoves` using `move_subject`, `scheduleProposal`, and allowlisted `occurrenceActions`. The app resolves and atomically relocates a subject bundle and its cards between owned activities; conversation history stays in its original thread as an audit trail.
- The approved catalog and recipe hints live in `bridge/component-catalog.mjs`; `app/activity-record-model.ts` and `app/workspace-model.ts` are the authoritative validators.
- Read `COMPONENT_RELATIONSHIPS.md` before changing record ownership, product/device composition, workspace binding, or cross-activity moves. Visual nesting follows explicit `subjectKey` ownership; card adjacency is never a relationship.
- Universal scheduling is D1-authoritative: `schedule_patterns` and ordered steps resolve idempotently into dated `daily_plan_items`. `app/schedule-model.ts` owns the pure language/validators; `app/api/schedule-store.ts` owns resolution; `app/api/schedule-proposal-service.ts` owns confirmed Luna proposals. Never edit an activity definition to represent a one-day change.
- Site-wide Luna is a two-stage coordinator over the one global conversation: Luna low + Fast acknowledges and answers immediately, then a `global_refresh` may research linked sources, review the whole activity index, and emit validated `activityWorkRequests` into exact owned activity compilers. Child work keeps the global conversation ID, so progress and durable receipts return to the root feed. Never let the coordinator write activity records directly or ask a preference before supplied source evidence/current activity knowledge has been checked. Explicit one-pattern cadence changes remain direct and audited; broader schedule work requires a revisioned proposal and confirmation.
- Site-wide open loops use typed `capture_open_item` actions. D1 stores the capture first, the app deterministically files it into an owned activity `item_list`, and Today/Tomorrow activates only a dated occurrence without changing the activity's essential/extra role. Ambiguous destinations require clarification.
- Explicit creation of one recurring activity uses the coordinator's validated `activityCreation` action. The acknowledgement records `outcomeKinds`; creation outcomes require a committed creation or clarification, never a text promise or existing-activity handoff. Definition and schedule commit together with a source-message-keyed receipt; day resolution resumes after failure before success is reported. Bridge-authenticated `inspect-global` and `retry-global-message` operations support audited recovery of exact saved messages using stable retry keys.
- Keep `backups/production-routine-2026-08-21.json` as the known-good production activity/order snapshot and `/restore`-compatible recovery input. Do not overwrite it with local development data.
- The default day mode is a flexible checklist. The persisted `Day Timeline` setting owns clock placement and scheduling semantics; activity-length controls remain available in either mode.
- Mobile collapsed and expanded activities share one header contract. Expanded footers keep only the large Skip and Mark Complete actions.
- Read `DESIGN_SYSTEM.md` before changing UI. It is the visual and interaction source of truth; `PRODUCT_SPEC.md` owns behavior and `app/globals.css` implements the tokens.
- Product copy should sell the user's capability and transformation, not the mechanism. Lead with what the person can accomplish, feel, or become; mention setup steps, features, components, or Luna only when they are necessary to understand or use the interface.

## Development and deployment

- Local development: run `npm run dev`; it uses disposable local D1 data. Run `npm test` (build + app tests + gateway tests) and `npm run lint` before committing.
- Production has two surfaces over the same Sites-bound D1: the private owner/iteration app at `https://ideal-day-sites.example`, and the two-user password gateway at `https://ideal-day-gateway.example`. `vercel-gateway/` has no direct D1 access; it authenticates a signed session, asserts one of two allowlisted stable user IDs, and proxies to Sites with server-only credentials. Both Vercel users begin with separate blank onboarding data; the Sites owner identity and records remain unchanged.
- Git remotes: `sites` is the Sites source repository; `github` is the GitHub repository. `main` tracks `github/main`. A local commit deploys nothing.
- Sites publishing is manual and remains the primary app/D1 deployment path: validate, commit the exact source, obtain a short-lived Sites source credential, push that exact `HEAD` to `sites` with a per-command authorization header, package with the Sites hosting helper, save a version for the same commit SHA, deploy it privately, and poll to success. Never run a bare `git push` to `sites` or persist its credential.
- Vercel production deploys after every push to GitHub `main` through `.github/workflows/deploy-vercel.yml`. That workflow runs the full test/lint gate, builds `vercel-gateway/`, and deploys the `ideal-day` Vercel project. GitHub repository secrets hold the Vercel token, org ID, and project ID; Vercel Sensitive Environment Variables hold only password hashes, stable user IDs, session/gateway secrets, the Sites bypass token, and origin URL. Never commit or print these values.
- Deployment order matters when shared app code, identity, onboarding, or the gateway/origin contract changes: publish the exact commit to Sites first, verify it, then push the same commit to `github/main` so Vercel cannot get ahead of its origin. Gateway-only changes may go directly through GitHub after local validation. Vercel preview deployments stay disabled until they have an isolated backend and cannot write production D1.
